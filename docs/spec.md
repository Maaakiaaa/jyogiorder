# 文化祭モバイルオーダー — 開発ルール

## このプロジェクト

文化祭の1つの模擬店で使うモバイルオーダー。来場者のスマホ注文と、店頭注文を同時に走らせる。会計は現金。

**作業前に必ず `docs/spec.md`（設計仕様書）を読むこと。** すべての判断の根拠はそこにある。
`prototype/order-loop-simulator.jsx` は状態遷移とUIの検証済みプロトタイプ。共有stateをSupabaseに置き換える前提の参照実装として扱う。

## 絶対に守る前提（violate したら設計が崩れる）

会場のWi-Fiは混雑時に不安定になる。設計の良し悪しは「たくさん捌けるか」ではなく **「ピーク時にネットが不安定でも壊れないか」** で判断する。

1. **番号は端末ローカルで採番する。** `A-01` / `B-01` 形式。**Supabaseに採番させない**（auto-increment / sequence / RPCでの採番はすべて禁止）。DB採番はネット必須になり、混雑時に最初に詰まる。
2. **採番カウンタは必ず `localStorage` に永続化する。** 発行のたびに保存。これを怠るとリロードで `A-01` に巻き戻り二重採番が起きる。最も壊れやすい急所。
3. **番号発行は「支払い確定」ボタンの瞬間だけ。** QRスキャンは内容のプレビューにすぎず、番号を発行しない。
4. **固有ID（order id）は冪等キー。** 同じ固有IDが二度届いても新規注文を作らず、既存の番号を返す。二重スキャン・オフライン復帰時の二重同期を防ぐ。
5. **すべての状態遷移は取り消し可能にする。** 非エンジニアが操作する前提。誤タップから必ず戻せること。
6. **メニュー品目は物理削除しない。** `is_active = false` で隠す。注文明細には `name_snapshot` / `price_snapshot` を焼き付け、後からメニューを変えても過去の注文が壊れないようにする。
7. **フォールバックを常に用意する。** 番号返却＝購読→再取得→紙。呼び出し＝通知→ボード→口頭。Web Pushは任意層で、絶対に主役にしない（iOSはホーム画面追加時のみ届く）。

## 技術スタック

- Next.js（App Router）+ Supabase
- Supabaseの役割は3つだけ：**DB** / **リアルタイム配達経路** / **売上記録**。採番はしない。
- 認証なし。来場者はQRからページを開くだけ。
- Web Push送信は Supabase Edge Function に置く。

## ルート構成

| パス | 画面 |
|---|---|
| `/` | 来場者の注文（カート → QR表示 → 番号・状態） |
| `/pos/a` | A端末（QR読み取り・会計・`A-xx` 発行） |
| `/pos/b` | B端末（店頭入力・会計・`B-xx` 発行） |
| `/kitchen` | 調理ディスプレイ（番号＋品目・完了） |
| `/board` | 呼び出しボード（完了かつ未受け渡し） |
| `/admin` | メニュー管理（品目・価格・売り切れ） |

## 実装上の注意

- 中身のほぼ全部がブラウザ側の処理（オフライン・ローカル採番・リアルタイム購読）。各画面は `'use client'` を付ける。SSRに寄せない。
- リアルタイム購読は電波が細ると切れる。**自動再接続だけに頼らず、画面表示時と再接続時に現在状態を一度取得する保険を必ず入れる。**
- 状態は `受付 / 調理中 / 完了 / 受け渡し済み / 取消`。`完了` を押した1イベントに、ボード表示・画面内更新・プッシュの3経路がぶら下がる。
- 呼び出しボードは「受け取り可能（`完了` かつ未 `受け渡し済み`）」を主表示としつつ、「受け取り待ち（`受付` / `調理中`）」も並べて表示する。お客さんが自分の番号が処理中に入っていることを確認できるようにするため。

## コードの方針

- 迷ったら、複雑さより「当日壊れないこと」を選ぶ。
- 楽観的UIより、状態が正しく見えることを優先する（誤表示は現場の混乱に直結する）。
- エラーは黙って握りつぶさない。ただしWeb Pushの購読失敗だけは静かに諦めてよい（非依存のため）。
