# 既存コードのリファクタリング手順

既存の実装を、`docs/spec.md` の設計に沿って**その場で上書きしながら**作り替える。

## 判断基準（最重要）

残す／潰すの審判は **仕様書** が行う。「動いているから残す」で判断しない。

> **仕様書と矛盾するものは、動いていても潰す。**

前回の実装には、今回却下した設計（DB採番など）が含まれている可能性が高い。それが生き残ると、新旧の思想が混ざったキメラになり、当日いちばん壊れやすい形になる。

## 着手前

1. `git commit` して作業ブランチを切る（例：`refactor/spec-v2`）。**これをやらずに始めない。**
2. `docs/spec.md` と `CLAUDE.md` を読む。
3. 既存コードを読み、下の「棚卸し」を Markdown で出力してから作業に入る。

## フェーズ0：棚卸し（コードを書く前に）

既存ファイルを一覧し、それぞれを3分類する。分類の理由を1行ずつ添えること。

- **残す**：仕様と矛盾せず、そのまま使える（例：メニュー表示のUI、Supabaseクライアント初期化、スタイル）
- **作り替える**：目的は正しいが実装が仕様と食い違う（例：DB採番になっている会計処理）
- **捨てる**：今回の設計に存在しない概念

**この棚卸しを提示して確認を取ってから、フェーズ1に進む。** いきなり全書き換えを始めない。

## フェーズ1：土台（順序を守る）

1. **データモデルを仕様に合わせる。** `categories` / `menu_items` / `orders` / `order_items` / `push_subscriptions`。既存テーブルとの差分をマイグレーションで埋める。`is_available` / `is_active` / `*_snapshot` を必ず入れる。
2. **採番をDBから端末へ移す。** ここが今回最大の作り替え。DB側の採番（sequence / auto-increment / RPC）を撤去し、`localStorage` で永続化するローカル採番に置き換える。`A-` / `B-` のプレフィックスは端末ごとの設定値として持つ。
3. **固有IDを冪等キーとして通す。** 注文組み立て時にクライアントで生成し、QRに含め、`orders.id` にする。同一IDのinsertは新規作成せず既存を返す。

## フェーズ2：画面

`prototype/order-loop-simulator.jsx` の状態遷移とUIを、ルートごとに分解して移植する。プロトタイプの `useReducer` による共有stateが、そのままSupabaseの購読に置き換わる。

`/` → `/pos/a` → `/pos/b` → `/kitchen` → `/board` → `/admin` の順に着手する。番号ループ（注文→採番→番号返却→完了→呼び出し）が一周する所までを最優先し、`/admin` は後回しでよい。

## フェーズ3：耐障害性

1. 購読の再接続時・画面表示時の**現在状態の再取得**（保険）。
2. 番号が戻らないときの**タイムアウト表示**（「レジで番号を確認してください」）。
3. オフライン時のローカルキューと、復帰時の同期（冪等キーで二重登録を防ぐ）。
4. Web Push（任意層）。失敗は静かに諦める。

## 各ステップの完了条件

- 変更のたびに、番号ループが一周することを確認する。
- **仕様を変える判断が必要になったら、勝手に決めずに聞く。** 仕様書側を直すべきケースがある。
- コミットは意味のある単位で分ける（棚卸し / 採番移行 / 画面ごと）。まとめて1コミットにしない。
